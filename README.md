# Решение

## Условия проекта

Приложение состоит из четырёх компонентов:

| Компонент | Тип нагрузки | Копий | RAM на копию | CPU на копию |
|---|---|---:|---:|---:|
| Database | Отказоустойчивая БД | 3 | 4 ГБ | 1 |
| Cache | Отказоустойчивый кеш | 3 | 4 ГБ | 1 |
| Frontend | Раздача статики | 5 | 50 МБ | 0.2 |
| Backend | Обработка запросов | 10 | 600 МБ | 1 |

Приложение планируется упаковывать в Helm-чарт и разворачивать в разных окружениях. Для БД и кеша используются по 3 реплики, чтобы переживать отказ одного экземпляра без потери доступности.

## 1. Расчёт ресурсов приложений

Расчёт выполнен по запрашиваемым ресурсам (`requests`) для CPU и памяти.

| Компонент | Копий | RAM на копию | CPU на копию | RAM всего | CPU всего |
|---|---:|---:|---:|---:|---:|
| Database | 3 | 4 ГБ | 1 | 12 ГБ | 3 |
| Cache | 3 | 4 ГБ | 1 | 12 ГБ | 3 |
| Frontend | 5 | 50 МБ | 0.2 | 0.25 ГБ | 1 |
| Backend | 10 | 600 МБ | 1 | 6 ГБ | 10 |
| **Итого** | **21** | — | — | **30.25 ГБ** | **17 CPU** |

Таким образом, для работы всех Pod требуется:

- **30.25 ГБ RAM**;
- **17 vCPU**.

## 2. Запас на рост нагрузки

Закладываем запас **20%**. Он нужен для:

- увеличения количества реплик backend или frontend;
- пикового потребления памяти;
- обновлений приложений без простоев;
- временного размещения дополнительных Pod.

| Ресурс | Требуется приложениям | Запас 20% | Итого с запасом |
|---|---:|---:|---:|
| RAM | 30.25 ГБ | 6.05 ГБ | **36.3 ГБ** |
| CPU | 17 | 3.4 | **20.4 vCPU** |

## 3. Учёт отказа одной worker-ноды

Кластер должен продолжать обслуживать нагрузку при выходе из строя одной worker-ноды. Поэтому недостаточно подобрать суммарную ёмкость впритык: после потери одной ноды оставшиеся worker-ноды должны вместить все Pod.

Выбираем worker-ноды следующей конфигурации:

- **8 vCPU**;
- **16 ГБ RAM**;
- **100 ГБ SSD**.

Из 8 vCPU и 16 ГБ RAM часть ресурсов резервируется под ОС, kubelet, container runtime, kube-proxy и системные Pod. Для расчёта принимаем доступно для приложений примерно:

- **7 vCPU**;
- **14 ГБ RAM** на одну worker-ноду.

| Количество worker-нод | Доступно CPU | Доступно RAM | Достаточно после потери одной ноды? |
|---:|---:|---:|---|
| 3 | 21 vCPU | 42 ГБ | Нет: после потери одной ноды останется 14 vCPU, а нужно 20.4 vCPU |
| 4 | 28 vCPU | 56 ГБ | Да: после потери одной ноды останется 21 vCPU и 42 ГБ RAM |

Следовательно, выбираем **4 worker-ноды**.

При отказе одной worker-ноды остаётся:

- **21 vCPU**;
- **42 ГБ RAM**.

Этого достаточно для 20.4 vCPU и 36.3 ГБ RAM, необходимых приложениям с запасом.

## 4. Служебные ресурсы

На каждой ноде часть ресурсов потребляют:

- операционная система;
- kubelet;
- container runtime;
- kube-proxy;
- CNI, например Calico;
- мониторинг и логирование, если они установлены;
- системные компоненты control plane на master-нодах.

Для worker-нод заложен резерв примерно **1 vCPU и 2 ГБ RAM**. Поэтому из физических 8 vCPU и 16 ГБ RAM для приложений считается доступным 7 vCPU и 14 ГБ RAM.

Для control-plane нод накладная нагрузка выше: там работают `kube-apiserver`, `etcd`, `kube-controller-manager` и `kube-scheduler`. Поэтому для них выбраны отдельные ноды с 4 vCPU и 8 ГБ RAM.

## 5. Итоговая конфигурация кластера

| Роль | Количество | vCPU | RAM | Диск | Назначение |
|---|---:|---:|---:|---:|---|
| Control plane | 3 | 4 | 8 ГБ | 100 ГБ SSD | `kube-apiserver`, `etcd`, `kube-controller-manager`, `kube-scheduler` |
| Worker | 4 | 8 | 16 ГБ | 100 ГБ SSD | Database, Cache, Frontend, Backend |
| **Итого** | **7** | — | — | — | — |

### Почему 3 control-plane ноды

Три control-plane ноды обеспечивают отказоустойчивость Kubernetes API и etcd. При недоступности одной control-plane ноды кластер сохраняет кворум и продолжает работать.

### Почему 4 worker-ноды

Четыре worker-ноды дают достаточную ёмкость для всех приложений, запас на рост и возможность пережить отказ одной ноды. После выхода из строя одной worker-ноды оставшиеся три ноды сохраняют достаточно CPU и RAM для работы всех компонентов.

## 6. Итог

Для проекта рекомендуется кластер из **7 нод**:

- **3 control-plane ноды**: 4 vCPU, 8 ГБ RAM, 100 ГБ SSD каждая;
- **4 worker-ноды**: 8 vCPU, 16 ГБ RAM, 100 ГБ SSD каждая.

Такая конфигурация обеспечивает:

- 17 vCPU и 30.25 ГБ RAM для приложений;
- 20% запаса на рост нагрузки;
- работоспособность при отказе одной worker-ноды;
- отказоустойчивость control plane из трёх нод;
- резерв на системные компоненты Kubernetes.
